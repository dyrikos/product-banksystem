# Практична 1. Розбір готового продукту: BankSystem

**Автор:** Юра Кампов, спеціальність F2 «Інженерія програмного забезпечення» · **Дата:** 09.11.2026

**Продукт:** BankSystem — консольна банківська система на C++: вхід за номером рахунку й PIN, баланс, поповнення, зняття, переказ, відкриття рахунку; дані зберігаються між запусками.

## 1. Код проти продукту

Перша версія — це **лише код**: один файл `legacy/12main.cpp` (~190 рядків). Щоб нею могла скористатися інша людина, у постачання входить ще:

| Складова | Що це в BankSystem | Де лежить |
|---|---|---|
| Документація для користувача | інструкція: меню, повідомлення, що робити при помилці | `5-management/user-guide.md` |
| Документація для розробника | README, контракт модулів, ADR, формат сховища | `README.md`, `2-architecture/`, `3-implementation/` |
| Інсталяція й оновлення | збірка однією командою CMake на Windows і Linux; статичний `bank.exe` без DLL | `CMakeLists.txt`, `5-management/runbook.md` |
| Ліцензія й правила | MIT; попередження «навчальний проєкт, не для справжніх грошей» | `LICENSE`, `5-management/privacy.md` |
| Підтримка | GitHub Issues за шаблоном, пріоритети P1–P4 | `.github/ISSUE_TEMPLATE/`, `5-management/support.md` |
| Сумісність | C++17; GCC, Clang, MSVC; CI на Ubuntu і Windows | `.github/workflows/ci.yml` |
| Дані | сховище рахунків, резервна копія, відновлення | `3-implementation/data-model.md`, runbook |

**Скільки з цього бачить студент, коли каже «я написав програму»?** Лише перший файл. Інструкція збірки, збереження даних, ліцензія, підтримка й сумісність — це окрема робота, і в v0.1.0 її не було взагалі: інша людина навіть не знала б, як зібрати програму і які PIN у демо-рахунків.

## 2. Модель життєвого циклу

**Модель: інкрементна.**

За схемою: **вимоги змінюються під час розробки? Так** — після першої робочої версії зʼявилась вимога «записувати дані користувачів» (CR-01), потім «відкривати рахунки» (CR-04). **Замовник доступний постійно? Ні** — викладач бачить проєкт на парах. → **Інкрементна.**

Обґрунтування:

- **Перша версія вже працювала** — вхід і 4 операції. Наступні версії не переписують її, а додають шари: v0.2 — модулі, збереження, тести; v0.3 — історія й безпека PIN.
- **Ціна помилки помірна, але не нульова:** неправильна сума — найгірший дефект банку, тому кожен інкремент закінчується зеленими тестами.
- **Незалежна перевірка — як виходять версії:** v0.1.0 → v0.2.0 → v0.3.0 → v1.0.0 привʼязані до контрольних точок курсу ([release-plan](../5-management/release-plan.md)). Кожна — робоча програма з новою функцією.

## 3. Ціна помилки на реальній ваді

**Вада (BUG-01):** гроші зберігались у `double`. Наслідок, знайдений тестом: на рахунку 0.30, клієнт знімає 0.10 — програма пише «Remaining balance: $0.20» — і далі **не дає зняти 0.20**: «Insufficient funds». Насправді на рахунку `0.19999999999999998`.

1. **На якому етапі зʼявилась?** На **проєктуванні**: коли для балансу обрали тип даних. Вимоги («гроші мають бути точні до цента») не було сформульовано взагалі, тож проєктувальник не мав чим перевірити вибір.
2. **Скільки коштувало б виправити тоді?** Хвилини: написати `long long cents` замість `double balance` у структурі, поки код ще не написано.
3. **Скільки коштує зараз?** Окремий модуль `money` з розбором і виведенням сум, зміна типу в усіх операціях, ADR-0002, 5 тестів на гроші й регресійний тест. Плюс 3 вже знайдені дефекти навколо сум (BUG-01, BUG-03). Якби програма працювала зі справжніми грошима — ще й перерахунок усіх балансів, у яких накопичилась похибка.

**Висновок:** дефект проєктування коштує в десятки разів дорожче за дефект коду, бо від типу балансу залежить кожна операція.

## Питання для захисту

- **Чому інкрементна?** Перша версія вже працювала, а нові вимоги зʼявлялись після неї; замовник доступний лише на парах — тому плановані версії під контрольні точки.
- **Чому вада зʼявилась на проєктуванні?** Тип балансу — рішення проєктування; код лише виконав його. Без вимоги про точність не було чим це рішення перевірити.
